DIP-06
======

One-shot nostr queries over HTTP
--------------------------------

`draft` `optional`

This DIP defines a stateless HTTP resource that answers a single NIP-01 filter
and returns the matching stored events as one JSON array. It is a **read-only
subset** of a relay: no `EVENT`, no subscriptions, no `EOSE`, no `AUTH`.

The purpose is cacheability. A websocket relay cannot be cached by a CDN; a
`GET` whose URL fully determines its answer can be. A client that only needs a
handful of well-known events — an install page reading NIP-82 release events,
say — should not have to open a websocket, and a relay operator should not have
to serve one.

This DIP does **not** replace NIP-01. It imposes nothing on relays: a
conforming implementation may be a relay, a gateway in front of one, or a
static index that holds only a few kinds. Nothing in NIP-01 changes.

## Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
interpreted as described in [RFC 2119][rfc2119].

A **server** is an implementation of the resource defined here. A **client** is
anything that makes requests of it. The **query value** is one filter encoded
as an [nfilter](05.md). **Filter**, **event**, and the matching rules are
NIP-01's, unchanged.

## The query value

The query value is one NIP-01 filter, encoded as a query string by
[DIP-05](05.md):

```
%23d=com.damus.notedeck%400.8.0&authors=<64 hex>&kinds=30063
```

That document is normative here and this one does not restate it. What it
defines and this DIP relies on:

* the field names and their value shapes — `ids`, `authors`, `kinds`,
  `since`, `until`, `limit`, and `%23<letter>` tag filters;
* percent-encoding, including that `#` is always `%23` and `,` separates the
  elements of a multi-valued field;
* **canonical form** — pairs sorted, elements sorted and deduplicated, hex
  lowercased, escapes uppercased — which is what makes a URL a usable cache key;
* the refusals: an empty query value, a repeated key, an empty value, an
  unknown or unimplemented key, a malformed value.

A server MUST implement every field nfilter defines except `search` and
`relays`, and MUST refuse those two, which nfilter's own rule already requires
of a decoder that does not implement them. `search` is [NIP-50][nip50]: a
different feature with a different cost model, and a server that has a
full-text index and wants to answer it should specify that separately. `relays`
names relays to run a query against and this resource is one store.

A server MUST reject a query value that nfilter says to reject, and MUST accept
a non-canonical one, answering it exactly as it answers its canonical form —
same body bytes, same `ETag`.

### One filter per request

The query value is one filter. NIP-01's `REQ` unions an array of them; this
resource has no encoding for that array, because nfilter has none.

This is a deliberate narrowing and the reasoning is HTTP's. Batching filters
onto one `REQ` is a websocket habit: you have one socket, so you spend it
carefully. Here each query is a request with its own URL, its own `ETag` and
its own freshness lifetime, and a compound query is one cache entry that any of
its filters can invalidate. Two independent questions cache better as two
requests than as one.

A client wanting a union makes the requests and concatenates the answers.
Because each response is already sorted and each event carries its own id,
merging them is a sort and a deduplication the client was going to do anyway if
it displays them together.

### What a server chooses to answer

This document specifies a **format**: what a query value is, how it
canonicalises, and what a response to one looks like. It does not specify which
queries a server is willing to answer, any more than NIP-01 tells a relay which
REQs to serve. A server exists to serve some particular set of events and is
free to say so.

So a server MAY refuse any query outside the subset it serves — a kind range, a
set of authors, whatever bounds the corpus it is actually publishing — and a
server that does MUST document the subset. The refusal is a `400` whose message
names what would have been accepted, since that message is the only thing
telling a client what to send instead.

Two things this does not license. A server MUST NOT answer a refusable query
with a *narrowed* one: silently adding a constraint a client did not ask for is
the same failure as silently dropping an unknown field, and both report success
for a question that was not asked. And a server MUST NOT vary the subset by
requester, which would make the response a function of something outside the
cache key.

Note that nfilter has no encoding for NIP-01's unconstrained `{}`, so the
cheapest hostile query is simply unsendable. That is a property of the encoding
and **not** a policy: `since=0` is the same query and is perfectly sendable, so
a server that does not want to be walked still has to say which queries it
serves and refuse the rest. See "The unconstrained filter has no encoding" in
[DIP-05](05.md).

As a worked example: the deployment this document was written alongside exists
to serve one application's release metadata, so it answers NIP-82 software
asset and release events (kinds 3063 and 30063) and refuses every query that
does not constrain `kinds` to those. Its store holds nothing else. That is
policy, not protocol, and another deployment of this format would have its own
— which is why none of it appears in the caps below.

### Caps

A server MUST publish, in its documentation, values for:

* **`max_events`** — the greatest number of events any single response may
  carry. The reference implementation uses 500, matching NIP-01 relay practice.
* **`max_field_elements`** — the greatest number of elements one field of the
  query value may carry. This MUST be large enough to hold a realistic contact
  list; the reference implementation uses 1024.
* **`max_tag_value_bytes`** — the greatest length of a single tag filter value,
  measured on the decoded element.
* **`max_url_query_bytes`** — see "Transports".

A query value with a field carrying more than `max_field_elements` elements, or
a tag value longer than `max_tag_value_bytes`, MUST be rejected. These are
refusals rather than truncations for the same reason an unknown field is:
silently dropping part of a filter widens it.

There is no `max_filters`, because there is one filter.

## Transports

The query value is identical on every transport — the same query-string text,
byte for byte. This is the entire point of the design: the transport is
expected to change and the query is not.

### `GET`

```
GET /req?%23i=com.damus.notedeck&authors=<64 hex>&kinds=30063&limit=50
```

The request's query string **is** the query value. There is no wrapper
parameter: an nfilter is already a query string, and nesting one inside a
`filters=` parameter would percent-encode it a second time and give back
exactly the unreadability this format exists to avoid.

It follows that a server MUST reject a query parameter it does not recognise
rather than ignore it — every parameter is part of the filter, and nfilter
already requires that. It also follows that this resource cannot grow a
non-filter query parameter later without colliding with a NIP-01 field name;
that is accepted, and the body transports are where anything else would go.

A `GET` with an empty query string MUST be rejected, as nfilter rejects an
empty query value.

A server MUST reject a query string longer than `max_url_query_bytes` with
`414 URI Too Long`, and the error message SHOULD name a body transport. `414`
rather than `400` because it tells the client that a shorter query would have
worked, where `400` says the query was wrong.

The length is measured on the query string **as received**, which is also what
a client measures when deciding whether to switch transports. Both sides
measure the same bytes: unlike JSON in a parameter, an nfilter in a URL is
already its own encoding, so there is no encoded-versus-decoded asymmetry to
reason about. The reference value is **2000**: nginx allows roughly 8 KB and
Cloudflare roughly 16 KB, but what sits between a client and an origin is not
knowable in advance, and 2000 is under every common ceiling with room for the
scheme, host and path.

Clients SHOULD switch to a body transport at that threshold. In practice the
only queries that reach it are the ones carrying a contact list: 500 authors is
roughly 32 KB of hex, which no encoding brings under a URL ceiling.

### `QUERY`

```
QUERY /req
Content-Type: application/x-www-form-urlencoded

%23i=com.damus.notedeck&authors=<64 hex>&kinds=30063&limit=50
```

[RFC 10008][rfc10008] defines `QUERY` as safe, idempotent and cacheable with a
request body, with the request content participating in the cache key. That is
exactly this resource, and `QUERY` is the RECOMMENDED transport for query
values too large for a URL. Servers SHOULD support it.

### `POST` (interim)

```
POST /req
Content-Type: application/x-www-form-urlencoded

%23i=com.damus.notedeck&authors=<64 hex>&kinds=30063&limit=50
```

Servers MUST support `POST` with the same body, path and response as `QUERY`,
for as long as `QUERY` support in browsers, proxies and CDNs remains
incomplete. Clients that cannot emit `QUERY` use `POST`.

`POST` is the wrong verb: this operation is safe and idempotent, `POST`
promises neither, and that is precisely why no cache will store the response.
Servers MUST treat a `POST` to this resource as safe and idempotent regardless.

The body is the query-string text, under
`Content-Type: application/x-www-form-urlencoded`. It is **not** JSON, and a
server MUST NOT accept a JSON body as an alternative spelling. One query with
two encodings is how the two drift apart, and it would put the canonical-form
rules — the thing the caching rests on — in two places at once.

A server MUST require that content type on both body transports and MUST reject
a body sent under any other rather than guessing at it.

Nothing on either body path may be method-specific — no different parsing, no
method sniffing, no different response shape — so that adding `QUERY` is a
routing change and not a behaviour change.

A server MUST return the same body for a `GET` and for a `POST`/`QUERY`
carrying the same query value.

## The response

On success the status is `200` and the body is a JSON array of NIP-01 events,
with `Content-Type: application/json`:

```json
[{"id":"…","pubkey":"…","created_at":1,"kind":30063,"tags":[],"content":"","sig":"…"}]
```

There is no `EOSE`: it means "the stored events are finished", and a one-shot
response is finished when it ends. There is no envelope, no subscription id and
no count.

A query matching no events is `200` with `[]`. It MUST NOT be a `404`: the
resource exists and the answer is "nothing", which is a different fact from
"there is no such endpoint".

Events MUST be serialised exactly as stored. A server MUST NOT re-encode an
event — reordering its members or altering its number formatting is how a
signature stops verifying at the client.

An event MUST appear at most once in a response.

### Ordering

The response MUST be sorted by `created_at` descending, ties broken by `id`
ascending in lexical order.

The `created_at` half is NIP-01's ("Newer events should appear first, and in
the case of ties the event with the lowest id (first in lexical order) should
be first"); this DIP raises it from SHOULD to MUST and makes the tiebreak
normative, because the order is part of the `ETag` and an unstable order makes
every revalidation a miss.

### `limit`

`limit` is NIP-01's: the query returns at most its `limit` most recent matching
events.

A `limit` greater than `max_events` MUST NOT raise the cap. A server MUST clamp
rather than reject: the two queries differ by nothing an answer can express, so
refusing one is a worse answer than serving it. A server SHOULD clamp during
canonicalisation, so that every `limit` above the cap collapses to one cache
key rather than to many keys over one answer.

`limit=0` MUST return no events, per NIP-01.

A response MUST carry at most `max_events` events. A server MAY return fewer
events than `limit` would allow. Clients MUST NOT treat a short response as
proof that no further matching events exist.

### Errors

An error response MUST have a JSON object body with an `error` member whose
value is a string:

```json
{"error": "unknown field \"nonsense\"; expected one of ids, authors, kinds, since, until, limit or a %23<x> tag filter"}
```

The message is for a human reading a log. It is not normative and clients MUST
NOT parse it.

| Condition | Status |
|---|---|
| Query value absent, malformed, or rejected by any rule in "The query value" | `400` |
| `GET` query string longer than `max_url_query_bytes` | `414` |
| Body present under a content type other than `application/x-www-form-urlencoded` | `400` |
| Server failed to answer a well-formed query | `500` |

A server MUST NOT answer a rejected query with `200` and a partial result.

## Caching

A server MUST send `Cache-Control` on every response. With none, HTTP's
heuristic freshness lets a cache invent a lifetime, and the point of this
resource is that the lifetime is derivable from the query rather than guessed
at.

One rule binds, and it is the unsafe direction only: **a server MUST NOT give a
response a freshness lifetime longer than its answer is good for.** In
particular, a query that a newly published event could enter MUST be served
with no freshness lifetime at all — `no-cache`, or `max-age=0`. Over-promising
is the one caching mistake a client can neither detect nor recover from;
under-promising costs a request.

How long an answer that *is* bounded should be trusted is the server's own
tradeoff, and this DIP does not fix it. Servers SHOULD classify as below, and a
server that classifies nothing and sends `no-cache` on everything is
conforming — it has given up the advantage the design exists for, but it has
not violated anything, and a relay adding this resource should not have to
implement a freshness policy to do so.

| Class | Condition on the query value | `Cache-Control` |
|---|---|---|
| Anchored | `until` is present and is in the past | `public, max-age=<hours>` |
| Addressable | every `kind` is addressable (30000–39999), and `authors` and `%23d` are both present | `public, max-age=<minutes>` |
| Open-ended | anything else | `no-cache` |

The reference implementation uses 3600 and 60 seconds.

Why each class is drawn where it is:

* **Anchored.** No event published from now on can enter the answer. It is
  still a finite `max-age` and not `immutable`, because a backfill of older
  events can still change it.
* **Addressable.** The query names specific addressable events by
  `(kind, author, d)`. Their *contents* change when the author publishes a
  replacement, so the window is short rather than long.
* **Open-ended.** The answer changes the moment a matching event arrives.
  `no-cache` and not `no-store`: a cache MAY hold the response as long as it
  revalidates, and revalidation is cheap.

An `until` in the *future* bounds nothing — events published between now and
then still enter the answer — and MUST NOT be treated as anchored. That one
stays a MUST NOT because it is the unsafe direction: it is the easy way to
serve a stale answer under a long `max-age` while believing the query was
bounded.

### `ETag`

A server MUST send a strong `ETag` on every `200`.

The `ETag` SHOULD be computed over the concatenated `id` values of the events
in the response, in response order. Event ids are content hashes, so the id
sequence is already a digest of the body: two responses carrying the same ids
in the same order carry the same bytes, and an addressable event republished
with new content gets a new id rather than keeping the old one. Computing it
this way keeps the validator independent of how the events happen to be
serialised.

A server MUST support `If-None-Match` and MUST answer a match with `304` and no
body. A `304` MUST carry the `ETag`, the `Cache-Control` the `200` would have
carried, and the same `Content-Type`. (Omitting `Cache-Control` from the `304`
makes every subsequent read a revalidation, which throws away most of what the
cache was for.)

Two spellings of one query MUST produce the same `ETag`, which follows from
canonicalising before answering.

### `Vary`

A server that varies its response by request header — in practice
`Access-Control-Allow-Origin`, below — MUST send `Vary` naming those headers,
or a shared cache will serve one origin's response to another.

## CORS

The resource is expected to be read by browsers from other origins.

A server MUST answer `OPTIONS` on the resource with the CORS response headers,
and its `Access-Control-Allow-Methods` MUST list every transport it supports.

Note that `application/x-www-form-urlencoded` is a CORS-safelisted content
type, so a cross-origin `POST` to this resource is a **simple request** and is
not preflighted — one round trip rather than two, which is a small gift of
choosing the form encoding over JSON. Nothing rests on it: the response is
still unreadable to a page whose origin is not allowed, and the resource is a
safe read of public events either way.

`QUERY` is not a safelisted method, so it *will* be preflighted whatever the
content type. **A server adding `QUERY` support MUST add `QUERY` to
`Access-Control-Allow-Methods` at the same time**; browsers will block it
otherwise, whatever the server supports, and this is the most likely way to
ship `QUERY` support that does not work.

## Migrating to `QUERY`

For as long as `POST` is the body transport, the body transport is not cached
at any CDN. Origin-side caching still works; edge caching does not. This is the
cost of the interim and it is the thing `QUERY` buys back.

Canonical form is required on the `GET` path today and is, strictly, unobserved
on the `POST` path — nothing caches a `POST`. It becomes load-bearing again the
moment `QUERY` responses are cached, since RFC 10008 puts the request content
in the cache key. Servers MUST canonicalise on both paths so that the flip
changes nothing.

## Rationale, and what was considered

**Why not a websocket relay.** A read-only `GET` deletes a hardening list
rather than working through it: no `EVENT` frame, so no unauthenticated write;
no connections, so no connection caps or idle timeouts; no subscriptions, so no
per-connection subscription cap. It also keeps a nostr client out of the
browser — a page that needs a few events needs `fetch` and nothing else.

**Why a query string rather than JSON.** See [DIP-05](05.md), which is the
whole of that argument. In short: JSON percent-encoded into a URL costs more in
syntax than it carries in data, and is unreadable in every place a URL is
actually looked at.

**Why one filter per request rather than a union.** Covered above. The short
version is that a union is a websocket economy — one socket, so batch — and
over HTTP it costs the thing the design exists for, since a compound cache
entry is invalidated by any of its parts.

**Why not content-addressed queries.** Registering a filter and fetching
`GET /q/<hash>` for ever solves the URL-length problem properly and caches
beautifully: a contact list is stable, and two users with overlapping follows
share an entry. It is not adopted here because RFC 10008 makes it unnecessary,
and it adds a write path and server-side state to a design whose whole
advantage is having neither. It is worth revisiting if `QUERY` adoption stalls.

**Why not an encoding trick instead of a body transport.** A 500-author contact
list is roughly 32 KB of hex. base64url of it is *larger*; binary-packing the
32-byte pubkeys still leaves about 21 KB; and random pubkeys do not compress.
No encoding closes a 32 KB to 2 KB gap, which is why the body transport exists
and why adopting a shorter filter encoding did not remove the need for it.

## Prior art

Two earlier proposals for HTTP access to relays were opened against
`nostr-protocol/nips` and both were closed:

* **[PR #680][pr680]**, "NIP-101 HTTP REST API" (2023), proposed a REST API for
  publishing and reading events, with filters as comma-separated query
  parameters. Closed with: *"We should strive to have just one way of doing
  things… Opening WebSocket connections is not complex, creating one more
  implementation requirement for all relays is complex."*
* **[PR #966][pr966]**, "NIP-200: Nostr Over HTTP(S)" (2024), proposed `/req`
  and a chunked `/stream` endpoint as a general websocket alternative for weak
  networks. Closed with: *"The alleged benefits definitely do not justify
  breaking compatibility."*

Both objections are to **replacing** the websocket transport, and both land.
This DIP is deliberately not that:

* It is `OPTIONAL` and imposes no requirement on relays. A relay that ignores
  it is unaffected, and an implementation of it need not be a relay at all.
* It has no write path and no streaming, so it does not duplicate `EVENT` or
  subscriptions — it duplicates exactly the stored-event query, which is the
  one part of NIP-01 that is a pure function of the request.
* Its motivation is not "websockets are hard" but caching: the answer to a
  bounded query over a static corpus is cacheable at the edge, and no websocket
  design can be.

PR #680's comma-separated query parameters are worth noting as convergent: it
reached for the same shape DIP-05 specifies, for what look like the same
reasons. This DIP differs in canonicalising that encoding, which is what makes
it a cache key rather than merely a readable one.

Related and distinct: [NIP-45][nip45] (`COUNT`) reuses NIP-01 filters for a
different answer over the websocket transport; [NIP-86][nip86] is JSON-RPC over
HTTP on the relay's URI for *management*, authenticated with NIP-98, and shares
nothing with this but the word HTTP. getAlby's `http-nostr` is an
implementation of an HTTP-to-nostr bridge for NIP-47, webhook-based rather than
one-shot, and is not a NIP.

## Conformance

A machine-checkable conformance suite for this document — language-agnostic
fixtures plus a runner — is in [`nostr-req-conformance/`](nostr-req-conformance/).
It covers DIP-05's canonical form as well, since a server cannot be checked
against one without the other.
