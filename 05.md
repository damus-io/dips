DIP-05
======

A NIP-01 filter as a query string
---------------------------------

`draft` `optional`

This document defines **nfilter**: an encoding of one [NIP-01][nip01] filter as
an `application/x-www-form-urlencoded` query string.

It exists because a filter written as JSON and then percent-encoded into a URL
is unreadable. The notedeck install page's release query is 399 characters this
way:

```
/req?filters=%5B%7B%22%23i%22%3A%5B%22com.damus.notedeck%22%5D%2C%22authors%22%3A%5B%2232e18276...
```

and 117 characters as an nfilter, with everything that matters legible:

```
/req?%23i=com.damus.notedeck&authors=32e1827635450ebb3c5a7d12c1f8e7b2b514439ac10a67eef3d9fd9c5c68e245&kinds=30063&limit=50
```

The saving is not the point — a query carrying a 500-entry contact list is the
same 32 KB of hex either way, and no encoding fixes that. The point is that a
filter in a URL is something a person reads, in a log line, a CDN dashboard, a
bug report or a browser address bar, and JSON-in-a-query-parameter is not
readable in any of them.

nfilter defines a **format**, not a resource. It says nothing about what
answers a filter, over what transport, or which filters anyone is willing to
serve. [DIP-06](06.md) is one resource that carries nfilters;
`notedeck_columns/src/nfilter.rs` in [notedeck][notedeck] is the reference
implementation.

## Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
interpreted as described in [RFC 2119][rfc2119].

**Filter**, **event**, and the matching rules are NIP-01's, unchanged. An
**encoder** produces an nfilter; a **decoder** reads one.

## One filter, not a list

An nfilter is **one** filter. NIP-01's `REQ` carries an array of filters and
unions them; nfilter has no encoding for that array and does not want one.

Over a websocket you batch filters because you have one socket to spend. Over
HTTP that constraint is absent, and a union is better expressed as several
requests: each gets its own URL, its own validator and its own freshness
lifetime, where a compound query is one cache entry that any of its filters can
invalidate. A caller that wants a union makes the requests and concatenates the
answers.

## Grammar

```
nfilter    = pair *( "&" pair )
pair       = key "=" value
key        = "ids" / "authors" / "kinds" / "since" / "until" / "limit"
           / tag / "search" / "relays"
tag        = "%23" ALPHA          ; "#" followed by one a-zA-Z
value      = element *( "," element )
element    = *( unreserved / pct-encoded )
unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~"     ; RFC 3986
pct-encoded = "%" HEXDIG HEXDIG
```

An nfilter MUST NOT be empty: it carries at least one pair. See "The
unconstrained filter has no encoding", below.

## Fields

| key | value | NIP-01 field |
|---|---|---|
| `ids` | comma-separated 64-character lowercase hex | `ids` |
| `authors` | comma-separated 64-character lowercase hex | `authors` |
| `kinds` | comma-separated non-negative decimal integers | `kinds` |
| `%23<letter>` | comma-separated encoded elements | `#<letter>` tag filter |
| `since` | non-negative decimal integer | `since` |
| `until` | non-negative decimal integer | `until` |
| `limit` | non-negative decimal integer | `limit` |
| `search` | one encoded element | [NIP-50][nip50] `search` |
| `relays` | comma-separated encoded elements | (see below) |

`ids`, `authors`, `kinds` and tag filters are **sets** — order carries no
meaning and a repeat contributes nothing — which is what licenses sorting and
deduplicating them in canonical form. `since`, `until` and `limit` are single
values.

A decoder MUST reject a key not in this table. **It MUST NOT ignore one.**
Dropping an unrecognised constraint widens the query rather than narrowing it,
and answers a question that was not asked: `kinds=1&nonsense=x` with the second
pair dropped is "every kind 1 there is". The same applies to a key in the table
that the decoder does not implement — `search` on something with no full-text
index, say. Refusing is the only answer that tells the caller the truth.

### `search` and `relays`

These two are in the grammar because the reference implementation emits them
and a format that cannot describe its own reference implementation's output is
not much of a format. Their *encoding* is defined here; their *meaning* is not
this document's.

* `search` is [NIP-50][nip50]'s, and is a single element rather than a list.
* `relays` has no NIP-01 or NIP-50 definition. It comes from nostrdb's filter
  model, where it names the relays a filter is meant to be run against. It is
  meaningful to a client routing a query across relays and meaningless to
  anything answering from a single store.

A decoder that does not implement either MUST refuse it, per the rule above.

## Percent-encoding

Every byte of an element that is not `unreserved` MUST be percent-encoded.
That is stricter than a URL requires — `@` and `:` would both survive
unescaped in a query string — and it is what makes the encoding decidable in
one direction: given an element, exactly one encoding of it is legal, so two
encoders cannot disagree.

Percent-escapes MUST use uppercase hexadecimal digits (`%2C`, not `%2c`), per
[RFC 3986][rfc3986] §6.2.2.1.

Three consequences worth stating rather than deriving:

* **`,` is the element separator**, so a literal comma inside an element is
  `%2C` and there is no ambiguity about where an element ends. Likewise `&`
  (`%26`) and `=` (`%3D`).
* **`#` is always written `%23`**, in the key of a tag filter and anywhere it
  appears in a value. Unescaped, it would start a URL fragment and everything
  after it would never reach the server. The key remains `#<letter>` — this is
  a spelling rule at the wire, not a rename.
* **`+` is a space**, as `application/x-www-form-urlencoded` defines it. A
  decoder MUST decode it that way. An encoder never emits a bare `+`, since a
  literal plus is not unreserved and encodes as `%2B` — so the media type's
  reading and a plain percent-decoding reading never disagree on a
  well-formed nfilter.

Hex in `ids` and `authors` is entirely unreserved, so those values are
unaffected by any of this and appear verbatim.

## Elements are text

An element is text. This encoding does **not** distinguish an element that is a
32-byte identifier from a string of the same 64 characters: a `#e` tag filter
naming an event id and a `#e` tag filter matching a literal 64-character string
encode identically.

Nothing is lost, because NIP-01 does not distinguish them either — its tag
filter values are JSON strings in both cases, and matching is over the tag's
text.

It does become a decision for a decoder targeting a *typed* filter model, and
such a decoder MUST document its rule. notedeck's takes any 64-character hex
element as an identifier, which is why a `#d` value that happens to be 64 hex
characters does not survive a round trip through it. A decoder targeting a
model whose tag elements are strings — or one that keeps NIP-01's own JSON —
has no such rule to make and no such wart.

## Canonical form

Canonical form exists so that **two spellings of one query are one string**.
Wherever an nfilter is a cache key — a URL, most obviously — a second spelling
is a second entry over one answer, and the caching quietly stops working.

An nfilter is in canonical form when:

1. **pairs are sorted** by their encoded key, comparing bytes;
2. **the elements of `ids`, `authors`, tag filters and `relays` are sorted** by
   their encoded text, comparing bytes, and deduplicated;
3. **the elements of `kinds` are sorted numerically** and deduplicated;
4. `ids` and `authors` elements are **lowercase** hex;
5. every element is percent-encoded as above, with uppercase escapes;
6. integers are written as decimal with no sign, no leading zeros and no
   fraction;
7. every pair present has a non-empty value (an empty one is a rejection, per
   "Refusals" below, rather than something to canonicalise away).

Rule 3 is the one exception to rule 2, and it is load-bearing: `kinds` sorted
as text gives `1,30063,7`, which is a different string from `1,7,30063` for the
same set.

### Why the sort is over the encoded text

An encoded element is ASCII by construction — unreserved characters, `%`, and
hex digits, and nothing else. So "compare bytes" is every language's default
string comparison, and there is no way to get it subtly wrong.

A rule stated over *decoded* elements would not have that property. Sorting
decoded strings correctly means comparing by Unicode code point, which is
equivalent to UTF-8 byte order and is **not** equivalent to UTF-16 code-unit
order — and UTF-16 code-unit order is exactly what JavaScript's
`Array.prototype.sort()` produces. The two disagree for any string containing a
character outside the Basic Multilingual Plane, so a JavaScript encoder written
against the obvious reading of a decoded-order rule emits a second cache entry
for one query, for one class of input, silently.

Sorting the encoded text costs a property in exchange: it is not the same order
as sorting the values. Percent-encoding maps every non-unreserved byte to a
sequence beginning `%` (0x25), which sorts below every unreserved character, so
the two orders disagree wherever one element has an escape at the position the
other has an unreserved character — `A` and `{` sort in one order decoded and
the other encoded. Nothing depends on the order being meaningful. Canonical
form needs *a* total order that every implementation computes identically, and
this is the one that is hardest to implement wrongly.

### Producing and accepting

An encoder MUST produce canonical form.

A decoder MUST accept a non-canonical nfilter and MUST treat it as the query it
denotes — same events, same answer — rather than rejecting it or answering
differently. Being non-canonical is not an error; it costs the caller a cache
miss and nothing else.

A decoder MUST NOT rely on the spelling it received when producing anything
derived from the query. Canonicalise first, then use the canonical form.

## Refusals

A decoder MUST reject an nfilter that:

* is empty;
* has a pair with no `=`, or with an empty value (`kinds=`). An empty value is
  ambiguous between "matches nothing" and "no constraint", and the two readings
  differ by the entire store — the same ambiguity NIP-01 leaves in `{"kinds":[]}`;
* repeats a key (`kinds=1&kinds=2`). A repeated key is the ordinary query-string
  idiom for a list, and this encoding spells a list with commas instead, so a
  repeat is an encoder that got the format wrong rather than a caller with
  something to say. Refusing says so;
* carries a key not in the field table, or one the decoder does not implement;
* carries a value of the wrong shape for its key — hex that is not 64 lowercase
  hex characters, an integer that is negative or fractional, a tag key whose
  letter is not `a-zA-Z`;
* contains a percent-escape that is malformed or does not decode to valid UTF-8.

A tag key's letter is `a-zA-Z` because that is what NIP-01 indexes. `%231` is
not a tag filter and is refused as an unknown key, rather than quietly becoming
a filter on a tag nobody writes.

## The unconstrained filter has no encoding

NIP-01's `{}` — the filter constraining nothing, matching every event — cannot
be written as an nfilter. The encoding of a filter with no fields is the empty
string, and the empty string is a refusal.

This is a real limitation and is stated rather than hidden. Two things follow:

* An empty query string and an absent one are the same thing to a decoder.
  A resource carrying nfilters therefore cannot distinguish "no query" from
  "the unconstrained query", and does not have to try.
* It is **not** a substitute for a policy about what a server answers. A server
  that intends to serve unconstrained queries needs a spelling for one and this
  format does not give it a spelling; a server that intends to refuse them
  should refuse them explicitly and say so, because `{}` is not the only way to
  ask for everything — `since=0` is the same query and enumerating the
  spellings of "no constraint" does not work.

## Worked example

The notedeck install page asks for the release events published by one key for
one application. As a NIP-01 filter:

```json
{
  "authors": ["32e1827635450ebb3c5a7d12c1f8e7b2b514439ac10a67eef3d9fd9c5c68e245"],
  "kinds": [30063],
  "#i": ["com.damus.notedeck"],
  "limit": 50
}
```

As a canonical nfilter — pairs sorted by encoded key, so the tag filter leads
(`%` is 0x25, below every letter):

```
%23i=com.damus.notedeck&authors=32e1827635450ebb3c5a7d12c1f8e7b2b514439ac10a67eef3d9fd9c5c68e245&kinds=30063&limit=50
```

A `d` tag carrying a version shows the encoding rule doing something. The
element `com.damus.notedeck@0.8.0` has one character outside `unreserved`:

```
%23d=com.damus.notedeck%400.8.0
```

And a two-element tag filter, sorted and comma-joined:

```
%23t=bitcoin,nostr
```

## Prior art, and what was considered

**Why not JSON in a query parameter.** That is what this replaces, and it works
— it is exactly NIP-01's own encoding, which is worth something. It is given up
because every structural character of JSON (`[`, `{`, `"`, `:`, `,`) is
percent-encoded to three characters in a URL, so the syntax costs more than the
data: the worked example above is 273 bytes of JSON and 399 characters of URL,
against 117 for the same query as an nfilter. What is actually lost is
readability, and it is lost completely.

**Why not a compact binary encoding.** base64url of the same JSON is *larger*
than the JSON. Binary-packing the 32-byte fields helps a contact list and
nothing else, and it trades away the one property this format exists for.

**Why not content-addressed queries** — register a filter, `GET /q/<hash>` for
ever. That solves URL length properly and caches beautifully, and it is a
different design: it needs a write path and server-side state, and the hash is
not readable either.

**Why `%23i` rather than `i` or `tag.i`.** Dropping the `#` makes `ids` and a
`#i` tag filter collide at `i`, and a prefix invents a namespace where NIP-01
already has one. `#<letter>` is what NIP-01 calls the field, so it is what the
key is; `%23` is only how a `#` is written in a URL.
