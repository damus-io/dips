# Conformance suite: one-shot nostr queries over HTTP

Fixtures and a runner for [DIP-06](../06.md) and the query-string filter
encoding it carries, [DIP-05](../05.md). Point it at an implementation and it
says pass or fail.

```
node run.js --base http://localhost:8080
```

It checks the **format** — what a query value is, how it canonicalises, and
what a response to one looks like. Which queries a server is *willing* to
answer is that server's policy, out of scope for the spec and so absent from
these fixtures.

So a server that serves a subset of nostr will fail the cases outside that
subset, and those failures are not conformance failures. `damus-api` is one:
it answers only NIP-82 release queries, so every fixture built on some other
kind comes back `400`. `reference-server.js` has no such policy and is what the
full suite is meant to be run green against.

The value here is `fixtures.json`. `run.js` is a harness — it holds no
knowledge of the spec that is not in the fixture file, so a runner in another
language reads the same data and reimplements about a dozen primitives. That is
the point: the Rust endpoint and the TypeScript client get checked against a
written spec rather than against each other.

## Layout

| | |
|---|---|
| `fixtures.json` | every case, plus the cap `profile` and the corpus pubkeys |
| `run.js` | the runner. Node 20+, no dependencies |
| `corpus.json` | six signed events, for the `corpus` group |
| `reference-server.js` | an in-memory implementation of both specs, so the suite can be shown to run |

`corpus.json` is generated by `scripts/gen_nostr_req_corpus.js` in
[damus-io/api][api], which needs [`nak`](https://github.com/fiatjaf/nak). That
generator writes the file into its own tree — `damus-api`'s release-sync tests
compile the same corpus in — so regenerating means copying the result here.
Regenerating rewrites every `sig` and no `id` — BIP-340 signing mixes in
auxiliary randomness — so a signature-only diff is not a corpus change.

## Groups

| group | needs | what it covers |
|---|---|---|
| `core` | a server | the query value, validation, errors, transports |
| `caching` | a server | `Cache-Control` classes, `ETag`, `Vary` |
| `conditional` | a server | `If-None-Match` and `304` |
| `cors` | a server | preflight and `Allow-Origin` |
| `corpus` | `corpus.json` ingested | ordering, `limit`, escaping, exact results |
| `canonical` | `--canonicalizer` | canonical form, decoding. No server involved |
| `encode` | `--encoder` | canonical form, encoding. No server involved |

Everything except `corpus` and `canonical` runs by default and passes against
an **empty** store — every response is `[]`, which is the correct answer.

`corpus` needs the events in `corpus.json` present in the store under test, and
nothing else matching their queries. It is where the suite gets teeth: against
an empty store, every response has the same `ETag` and the canonical-form cases
pass without proving anything.

```
node run.js --base http://localhost:8080 --group corpus
```

`canonical` and `encode` need no server, and between them are how a client is
checked. `canonical` takes a command that reads a query value on stdin and
writes its canonical form on stdout — a decoder. `encode` takes one that reads a
NIP-01 filter as JSON and writes its canonical nfilter — an encoder.

```
node run.js --group canonical --canonicalizer 'node reference-server.js --canonicalize'
node run.js --group encode --encoder 'node reference-server.js --encode'
```

The two exist separately because most clients are only one of them. The website
builds the install page's query and never reads one back, so it has no decoder
to check and every canonical-form mistake it could make is an encoding mistake
— a silent cache miss rather than a wrong answer. `encode` is the group that
catches those. It is run against the website's `src/lib/notedeck/nfilter.ts`
like this:

```
node run.js --group encode --encoder 'node --experimental-strip-types encode.mjs'
```

where `encode.mjs` is three lines: read stdin, call `filterToQuerystring`, print.

There is no `optional` group any more. It held the two cases the JSON encoding
left ambiguous — a duplicate object member name, and whether `[{}]` is answered
— and the query-string encoding decides both: a repeated key is a refusal, and
NIP-01's `{}` has no encoding at all. `run.js` still supports a list for
`expect.status`, because the next such case will want it.

## Fixture shape

```json
{
  "name": "an-unknown-field-is-refused-not-ignored",
  "section": "The query value",
  "group": "core",
  "transport": "both",
  "query": "kinds=30063&nonsense=1",
  "note": "Ignoring it would widen the query to every kind 30063 in the store.",
  "expect": { "status": 400, "body": "error" }
}
```

`query` is always **raw text**, and the runner splices it into the URL or the
body without re-encoding it, so a fixture can carry malformed escapes, repeated
keys and non-canonical spellings exactly as they go on the wire. (Sending it
through `URLSearchParams` would turn `%23d` into `%2523d` and test a different
query than the one the fixture states.)

* `transport` — `get`, `post`, `both`, or `options`. `both` sends the query
  twice and additionally requires the two responses to be identical in body,
  `ETag` and `Cache-Control`; that is the "one shape, every transport" claim,
  checked for free.
* `generate` — instead of a literal `query`, one of `field_over_limit`,
  `tag_value_over_limit`, `url_over_limit`, built from `profile`. A deployment
  with different caps edits `profile` and no fixtures.
* `expect.status` — a number, or a list when the spec permits either answer.
  On a list, a `4xx` outcome skips the remaining assertions.
* `expect.headers` — `"value"` exact, `"~value"` contains, `"*"` present,
  `"@key"` the value of `profile.key`, `null` absent.
* `expect.no_freshness` — the response must carry no freshness lifetime. Unlike
  the `@key` header rules, this does not consult `profile`, which matters:
  classification is a SHOULD and the three `*_cache_control` values are what a
  deployment *declares*, not what the spec requires. A server that classifies
  nothing sets all three to `no-cache` and the whole caching group passes. This
  is the half that holds regardless.
* `expect.body` — `events`, `error`, or `empty`. Omit it to assert only on
  status and headers.
* `expect.ids` — the exact ordered event ids. `corpus` group only.
* `expect.checks` — `ordered`, `unique_ids`, `within_cap`, `matches_filter`,
  `empty`, `events_match_corpus`. `matches_filter` decodes the query value and
  runs NIP-01 matching over every returned event, which is the difference
  between testing headers and testing the query.
* `same_as` / `differs_from` — compare body and `ETag` against another case by
  name. This is how canonical-form equivalence is checked from outside.
* `if_none_match` — makes the case two requests: one to learn the validator,
  one to present it. `@etag` is substituted with what the first returned.

`canonical_cases` and `encode_cases` are separate lists with their own shape:
`input` (a query value) or `filter` (a NIP-01 filter as JSON), and the
`canonical` form expected out.

## Are these fixtures reachable?

Mutating `reference-server.js` and re-running the suite is the cheap way to
find out a fixture asserts something no implementation could get wrong. Nine
mutations, eight caught:

| mutation | caught by |
|---|---|
| no id tiebreak on equal `created_at` | 10 — the `ordered` checks directly, the `same_as` ones via a differing `ETag` |
| `limit=0` treated as unset | 2 — `limit-zero-returns-nothing` and its corpus twin |
| unknown keys ignored | 4 — `an-unknown-field-is-refused-not-ignored` and the tag-name cases |
| a repeated key taking the last value | 1 — `a-repeated-key-is-refused` |
| elements not re-encoded, so `%2c` and `%2C` differ | 4 — the whole encoding half of the `canonical` group |
| tag values matched before decoding | 3 — every corpus case with a `%23d` in it |
| oversized `GET` answered `400` | 1 — `an-oversized-get-is-414-not-400` |
| hex not lowercased | 2 — `hex-case-does-not-change-the-answer`, `canonical: hex-is-lowercased` |
| **response not capped at `max_events`** | **nothing** |

The last one is a real hole and not a fixable one at this size: with six events
in the corpus and a cap of 500, no request can reach the cap. Checking it needs
a corpus larger than `profile.max_events`, which is a different kind of fixture
— generated, not committed. Left undone deliberately.

The tiebreak row is why `corpus.json` is written in the *reverse* of response
order. With the corpus stored in response order, a server that never sorts at
all passed every ordering fixture — including the exact-ids ones — because
`Array.prototype.sort` is stable and the answer was already in the file.

Two mutations that the old JSON suite caught are gone with the encoding rather
than untested. "No deduplication across filters" has no filters to be across —
one query value is one filter — and "tag values sorted by UTF-16 code unit" is
unreachable, because canonical form sorts the *encoded* elements and those are
ASCII. That second one is the trade [DIP-05](../05.md) makes deliberately:
the ordering rule stops having a wrong answer a JavaScript client can reach.

## The reference server

`reference-server.js` implements both specs in memory. It is not a production
server: no rate limiting, no persistence, a linear scan of the store, and it
trusts `corpus.json` rather than verifying signatures. It exists so the suite
can be run green, and so a mutation can be shown to turn it red.

```
node reference-server.js --port 8080 &
node run.js --base http://localhost:8080 --group core,caching,conditional,cors,corpus
node run.js --group canonical --canonicalizer 'node reference-server.js --canonicalize'
```

## Known limits

* Nothing here checks that a **cache** behaves correctly — only that the server
  emits headers that would make it. Whether Cloudflare actually stores the
  response is not a property of the origin.
* The caching group checks two different things with two different strengths.
  Whether a server classifies the way the draft suggests is checked against its
  own declared `profile`, so it is a self-consistency check and a server that
  declines to classify passes trivially. Only `no_freshness` is checked against
  the spec itself. That asymmetry is deliberate: over-promising freshness is
  the one caching mistake a client cannot detect, and everything else is the
  server's tradeoff.
* The `ETag` is defined over event ids only, so two *different* queries that
  both match nothing share a validator. HTTP compares validators per resource
  and these are different URLs, so nothing is wrong; but it does mean
  `same_as` proves nothing against an empty store, and `differs_from` is in the
  `corpus` group for that reason.
* `matches_filter` proves every returned event *should* be there. Nothing
  proves an event that should have been returned was not silently dropped,
  short of the exact-ids fixtures in the `corpus` group.
* Nothing checks that a cross-origin `POST` is *not* preflighted. It follows
  from the content type being CORS-safelisted and is the browser's behaviour
  rather than the server's, so there is nothing here to assert it against.
